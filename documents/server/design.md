# 后端实现设计

当前为 Java21 / Spring Boot3.5 / Spring Security / Spring Data JPA / MySQL8.4 / Gradle 单体，无Redis、微服务、消息队列、分布式锁。接口以[当前契约](design-api.md)为准，数据库升级见[迁移说明](../database/design.md)。

## 认证与隐私

Spring Security Resource Server 统一验证 Bearer，Nimbus 实现 HS256 签名/验签，不自行实现 JWT 密码学。配置的 Base64 随机密钥至少32字节。校验签名算法、issuer、audience、subject、iat、nbf、exp、随机jti及用户authVersion；检查数据库角色/封禁、会话版本和持久化吊销记录。角色从数据库读取，JWT不赋予自报角色。改密、变更角色/封禁提升版本，旧会话失效；注销仅吊销当前jti。吊销表保留记录，不影响重启后检查；尚无过期吊销清理任务，可按expire_at离线归档。

密码 BCrypt cost12，72 UTF-8字节上限避免截断；旧数据默认禁用明文登录，采用显式scheme和一次性登录升级，绝不通过字符串前缀猜测哈希。请求与响应DTO分离，全局拒绝未知请求字段；User实体额外JsonIgnore密码作为防线。仅本人/管理员可取用户资料；订单仅交易参与人/管理员可取，待付款卖家不获取地址。管理员能力和归属在业务服务层执行，筛选始终与权限谓词相交。

## 库存、幂等和事务

创建订单使用 READ_COMMITTED 事务：锁买家用户行 → 查询已有幂等键 → 锁商品行（SELECT FOR UPDATE）→ 校验状态/时间/卖家/库存 → 写入单价/总额快照、扣库存、插入订单 → 一起提交。数据库唯一键作为额外防线。锁买家可序列化同一用户对不同商品使用同一键的竞争；代价是同一用户下单串行，适合课程规模。不同买家争抢最后一件时由商品锁序列化，后者看到已提交库存。只加Transactional无法防超卖，所以所有库存写路径必须遵守商品锁。

商品更新同样取得商品行锁。Item @Version在库存扣减/回补/发货和商品更新时递增；修改绝对库存要求客户端当前version，防止提交陈旧页面值覆盖已经发生的扣减。库存补货后还要有容量容纳可取消订单，避免整数溢出使回补失败。价格/上下架/时间修改均在锁内，和下单有明确先后；不能在锁外读取实体再save覆盖。

订单流转统一：先查itemId标量 → 锁商品 → 锁订单，不反向取锁。创建时是用户→商品，没有路径在持有商品锁时再锁用户，避免循环等待。取消在锁内先检查原状态，再一次性回补和关闭；状态已取消的重试不回补。支付与取消共享同一套锁，只有符合原状态的一方成功。MySQL死锁/锁超时返回409，客户端可按原幂等键重试。

总额以Math.multiplyExact(long, long)计算，价格/数量为非负/正INT，订单total为BIGINT分。数据库关联、CHECK、唯一键和索引由Flyway管理。事务插入订单失败会回滚库存；测试在真实MySQL上额外施加失败CHECK强制验证。

## 状态、超时和统计

0待支付→1待发货→2待收货→3完成。买家/管理员可取消0，卖家/管理员可取消1并标记模拟退款。已发货不取消，所有交易记录保留。通用更新路径仅作地址变更入口，空请求为400。商品下架不取消既有订单，封禁不修改既有交易，可由管理员履约/取消。

每张新订单持久化expiresAt；服务端严格在截止秒拒付。任务启动时及每60秒扫描过期待支付ID，按单独事务处理每笔（每轮至多100），失败不阻断其他订单；重复运行、多个实例、进程重启均靠状态+行锁保证只回补一次。大积压会分轮处理；目前适合课程规模，无高吞吐承诺。订单deadline按创建时配置冻结。

平台统计在可重复读事务内从数据库取快照。交易额包括已支付未取消订单（1/2/3），退款与取消排除；团购进行中同时考虑上架和半开时间区间。没有真实资金、支付回调、微信/短信/物流、上传、多地址簿或物理删除功能。
